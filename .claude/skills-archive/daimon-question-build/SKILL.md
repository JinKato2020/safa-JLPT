# 大問作成スキル — 一意性を担保して問題を量産する

> **成立の経緯**: 2026-07-17、言い換え類義(N4文レベル185・N3語レベル1000)の再生成で確立。
> **前史**: 用法で「Opus＋サブエージェント＋誤答6個」で作ったのに**一意にならなかった**（探す→「川で石を探した」「安い店を探した」が両方成立）。
> その失敗を潰すために作った手順。**他の大問(文脈規定・文法形式・組み立て・用法の作り直し)にそのまま使う。**

## 0. 鉄則（破ると必ず作り直しになる）

| # | 鉄則 | 根拠(実測) |
|---|---|---|
| 1 | **いきなり大量生成しない。必ず数問のパイロットで作り方を検証**。ただし**パイロットの"率"は信じるな**（作り方の検証にのみ使う） | 10問のパイロットで「N4=0%/N3=40%」と出たが、本走行335問では**N4=8.6%/N3=7.3%＝ほぼ同率**。5問の偶然に理屈を後付けして「文レベルは構造的に安全」と誤結論した |
| 2 | **独立の反証役を必ず置く。生成AIの自己検証は必ず漏れる** | 生成AIは「なぜ誤りか」の理由文を書いた**上で**コピー/熱気の第2正解を見落とした。独立Opusだけが捕捉 |
| 3 | **第2の正解を作るくらいなら誤答を減らす（6→5→4）** | 4択に必要な誤答は3個。無理に6個目をひねり出すのが一意性崩壊の主因 |
| 4 | **エージェント数を最小化（バッチ30前後・読むだけのagent禁止）＝既定はトークン最小の標準モード** | 用法で read67+gen67+verify67=201体・396万トークン→**セッション上限到達**。詳細=[[workflow-subagent-efficiency]]。※時間優先の**速度モード**は§10（並列上限内で意図的にagentを増やす・要ユーザー承認） |
| 5 | **品質の中核(誤答・訳・読み)は安価モデルに落とさない。Opus high** | 近接ダミーの質＝この作業の存在理由。medium で落ちる。手戻りの方がトークン浪費=[[quality-critical-gen-use-opus]] |
| 6 | **プールを増やす前に、engineが増えた誤答を使えるか確認** | 言い換えは `slice(0,4)`＝先頭3個固定で、6個入れても3個死蔵＋毎回同じで暗記されるところだった |
| 7 | **推測で数字を語らない。実測する** | 「在庫2085件」と説明したが実測1001件（2085は文脈規定の数字）。ユーザーの判断前提を壊した |
| 8 | **監査flagを鵜呑みにしない。三分類×確度で扱う（過検出が前提）** | 文法形式786問を「疑わしきはflag」＋2run和集合で監査→**35%(275件)**flag。全部を欠陥扱いして修理すると quota浪費＋誤修理。multi(真の一意性崩れ)/pair(誤答等価=軽微)/level に分け、both-run一致(高確度)とone-runで優先度化し、修理範囲は**実数提示でユーザーが決める**。詳細=§10 |

## 1. 手順（この順で回す）

```
① 公式PDFを実読 → 出題者の狙い・形式・ダミーの手口を抽出（レシピ化）
② 在庫データを実測（件数・構造・アプリが何を出題しているか）
③ engine側の前提を確認（誤答プールを使えるか＝動的3抽出があるか）
④ パイロット（各級5問）→ 生成＋独立反証 → ユーザーに提示して承認
⑤ 本走行（バッチ30）: 生成 → 独立【検証＋修理を一体化】→ 非一意/破格/誤答を修理
    ・修理は選択肢の差し替えだけでなく【必要なら本文も直して帳尻を合わせる】(情報源の補充/文末・時制の調整/語句入替/言い換え/前後の追記削除)。文章の文法・読解で特に有効
    ・検証役に「検証し、必要ならその場で直して最終版(本文＋4択＋正解)を返す」とさせ、自分の修理を再確認(鉄則3)
⑥ 【再検証】修理済みだけを独立にもう一度検査 → 残ったら誤答を1個落として確定
⑦ ゲート投入（検証済のみ出題）＋データ検証テスト
⑧ 記録（マージ）: 完了時に 学び・実績・作成時間・使用トークン・在庫問題数 を §11 にマージ（追記で別セクションを作らない）
```

**【検証＋修理は一体・本文も直す】**（2026-07-19 N3/N5/N4 文章の文法で確立・ユーザー方針）: すでに生成済みの問題を検証する時も、**「検証→修正→再検証」を1パスに統合**する。検証役に「一意性を判定し、必要ならその場で修理して最終版を返す」とさせ、**修理は空所の選択肢だけでなく、必要なら本文を修正して帳尻を合わせる**（情報源の補充・文末や時制の調整・語句入替・文の言い換え）。返り値=修正済みデータをそのまま採用し、別途【再検証】で残存second_answerを潰す。狙い＝適用ステップを消してトークンと往復を節約しつつ品質を上げる。

**開始前にモードを選ぶ**（§10）: 既定＝**標準**（トークン最小）。ユーザーが急ぎなら**速度モード**（トークン増で時間短縮・要承認）。

**実績（言い換え335問・2026-07-17）**

| 級/形式 | 規模 | 生成 | 反証が捕捉した非一意 | 再反証 |
|---|---|---|---|---|
| N3 語レベル | 150問 | 14体/567k | **11件(7.3%)** | 1件再発→誤答1個削除で確定 |
| N4 文レベル | 185問 | 16体/777k | **16件(8.6%)** | 検査 |

**非一意率は形式によらず約8%**。「文レベルは安全」はパイロット5問の偶然だった（→鉄則1）。
`answerFixed`（仮の正解が緩く自動修正）＝N3で21問(14%)・N4で5問。**元データの正解自体が信用できない**ことの証拠。

**④を飛ばさない。** レシピがズレていたら丸ごと無駄になる。

## 2. 作問レシピ（誤答の作り方＝全大問共通の核）

**狙い**: 正解が一意に定まること（[[unique-answer-question-design]]）。

**誤答の型（公式の手口）**
1. **同一意味フィールドで揃える**（位置語なら位置語だけ／量なら量だけ）＝分野で消せない
2. **同一品詞・同一文型スロット**＝文法で消せない
3. **連想の罠(near-miss)を必ず1つ**（くさる→まずくなった＝腐れば不味いが定義でない）
4. **方向違い・程度違い**（あまる↔ふえた／少なくなった）

**禁止**
- **荒唐無稽な分野違いダミー**（作法→天気/音楽/地図）＝当てずっぽうで消せる＝測定にならない。**現行アプリの欠陥そのもの**
- 個人名（役割ベースで書く＝[[content-borderless-no-names]]）

**★一意性テスト（ここで用法もパイロットも失敗した）**
- 各誤答を「文に代入 → 意味が保たれるか」テストする。少しでも成り立つ語は**第2の正解＝不可**
- **自分が確定した正解の近縁語を誤答にするな**（最頻出の失敗）

**実際の失敗例（プロンプトに必ず埋める）**
- 刷った→正解「印刷する」に誤答「コピーする」…「ポスターを百枚コピーした」は自然で意味が重なる＝失格
- 活気→正解「活力」に誤答「熱気」「エネルギー」…「町は熱気にあふれていた」も成立＝失格
- 探す→誤答「川で石を探した」「安い店を探した」…**両方とも正しい用法**＝失格（用法の実バグ）

**誤答の個数**: 原則6個 → 一意な6個目が作れないなら**5個** → それも無理なら**4個**。
`needsDrop=true` で申告させ、4個すら無理な語だけ在庫から差し替える。**減らすのは正当な判断で減点ではない。**

## 3. 反証役（独立verify）の設計 — 最重要

**生成役とは別のエージェント**に、**暴くことだけ**をさせる。

```
目的は【第2の正解】を暴くこと。厳しく判定せよ。
answer と各 distractor を代入し、同義が成り立つか判定。
少しでも成り立つものは valid。基準は緩めに(=疑わしきは valid にして拾う)。
実際に見逃された例: 刷る/印刷する に対する「コピーする」、活気/活力 に対する「熱気」「エネルギー」。
この水準の重なりは valid とせよ。
valid≥2 → verdict='multi'(非一意=fail) / answerのみ → 'unique' / answerすら不成立 → 'bad_answer'
```

- **基準は「疑わしきはvalid」**（甘い反証は無意味）
- `{id, validCount, validChoices, verdict, note}` を返させる
- `multi`/`bad_answer` の問題だけを**修理役**へ渡す（validChoices を削除→非同義な語に差し替え／無理なら減らす）

**なぜ独立が要るか**: 生成役に自己検証させると、理由文まで書いた上で見落とす（実証済み）。
自己検証は**必要だが十分でない**。

### ★修理した問題は必ず【再反証】する（2026-07-17 実証）
**修理役が新しい第2の正解を作る。** N3波1で11件を修理→再反証したところ**1件が再びmulti**だった。
- `出版`→正解「刊行」の修理で入れた新ダミー「**販売**」…「新しい辞書を販売した」は自然で**発売≒出版**と重なる＝第2の正解
- 再反証しなければこの不良品がそのまま出荷されていた
- **再反証は全件でなく修理済みだけ**でよい（11件なら1体・約38kトークン）。安い保険。
- **文法形式でも実証（2026-07-18）**: 261問を修理→再反証で **multi残存4・pair残存10**。誤答3個固定の形式でも修理役は第2の正解を生む＝再反証は形式を問わず必須。

**再反証で残ったら、追加生成せずに誤答を1個落とす。**
反証役の note が「他は不成立」と明示していれば、その語を削除して5個にするだけで確定＝**追加トークン0**。
`reasons` も同じ位置を落とす（個数・順序を保つ）。

## 4. Workflow の実装作法（ここで実際に事故った）

| 事故 | 症状 | 対策 |
|---|---|---|
| **args が undefined** | プロンプトに `入力(5問): undefined` と出て agent が空配列を返す。N4は成功しN3だけ全滅 | **argsを使わずスクリプトにデータをJSリテラルで埋め込む**。生成器で埋め込み、先頭データを目視確認 |
| **CRLF で実行拒否** | `script contains control characters` で起動できない | Pythonで書くなら `io.open(..., 'w', encoding='utf-8', newline='\n')`。**書き出し後に `assert b'\r' not in f.read()`** |
| **agentがnullを返す** | `.map`/`.items` でクラッシュ | `if (!gen \|\| !gen.items) return {items:[],results:[]}`／`.filter(Boolean)` |
| **cp932でprintが落ちる** | `UnicodeEncodeError` で救済スクリプトごと死ぬ | `sys.stdout.reconfigure(encoding='utf-8', errors='replace')` |
| **テキストモードで\rが見えない** | 制御文字スキャンが CR を見逃す | **バイナリで読む**（`io.open(p,'rb')`） |

**構成**: `pipeline(BATCHES, gen, verify→repair)` でバッチごとに独立して流す（バリア不要）。
バッチ=30問=全体の約10%＝「10%ごとにバックアップ」規定を構造的に満たす。

## 5. 救済3層（バッチ失敗時・必須）

| 層 | 仕組み | 効果 |
|---|---|---|
| 1 | `journal.jsonl` に**agent完了ごと自動追記** | 完了バッチは常にディスク上。落ちても消えない |

## 6. ゲート（未検証を出題しない）

**作り直し前の問題は出題もカバー率の母数も汚す**ので、検証済みだけ出す。

```ts
// data/index.ts: バンクの型に verified を足す
export interface XxxBankItem { ...; verified?: boolean; }

// data/daimon.ts: 検証済ユニットだけ出題
const SY_VERIFIED_UNITS = new Set(
  SYNONYM_BANK.filter((e) => e.verified === true).map((e) => `${e.id.slice(3)}#synonym`),
);
// daimonUnitIds 内
: daimon === 'synonym' ? items.filter((u) => SY_VERIFIED_UNITS.has(u)) : items
```

**注意（重大）**
- ゲートは**データが入るまでその大問を全級から消す**。**必ずデータと同じコミットで入れる**（単独pushするとビルドで大問が消滅）
- **母数が波ごとに増える**＝ユーザーのカバー率/合格率は新データ投入時に下がる（正しい挙動だが要説明）
- **スコープ外の級に注意**: N3/N4だけ作り直すと、ゲートでN5の大問が消える。級を絞るなら**ゲートも級で絞る**

## 7. engine側の前提（プールを増やす前に必ず確認）

**誤答を3個より多く持たせるなら、engineが動的に3個抽出しているか確認する。**

```ts
// data/daimon.ts — 全大問で共有
export function build4Choices(answer: string, pool: string[], rng: Rng) {
  const distractors = pool.filter((x) => x !== answer);
  const picked = distractors.length > 3 ? sample(distractors, 3, rng) : distractors;
  return shuffleChoices([answer, ...picked].slice(0, 4), 0, rng);
}
```
`slice(0,4)` のままだと **先頭3個しか出ない**＝残りは死蔵＋毎回同じ＝暗記される。
テストは **旧実装に戻すと落ちること**を必ず確認する（空回りテストを作らないため）。
※乱数テストは**1本のストリーム**を回す。連番シードで作り直すと初手が相関して特定の誤答が出ない（実際に踏んだ）。

## 10. 実行モード（標準＝トークン最小 ↔ 速度＝時間優先）

作業前に**どちらのモードか**を決める。既定は**標準**。ユーザーが「急ぎ／時間優先」と言ったら**速度モード**＝トークンを多めに使って壁時計時間を縮める。
**速度モードでも品質段（独立反証・再反証）は省かない**——省くのは"品質モード"であって速度モードではない。速度は「並列で波を畳む・直列段を減らす」で稼ぐ。

**原理（なぜ速くなるか）**: 壁時計時間 ≒ (波の数) × (1エージェントの所要) ＋ (直列段の待ち)。Opus high 1体は重い（例: 40問で十数分）。だから **(a)波を1つに畳む (b)直列段を減らす** が効く。並列上限は **min(16, コア−2)**（Workflow仕様）。

| 項目 | 標準（既定・鉄則4） | 速度（時間優先・要承認） |
|---|---|---|
| バッチ | 30〜40問（agent最小） | **バッチ=⌈総数 ÷ 並列上限⌉** で1波に畳む。1体の担当数を減らし全員同時に走らせる＝波が1つなら壁時計≒1体の所要 |
| 直列段 | gen→反証→修理→再反証（4段） | **投機で段を潰す**: ①生成時に誤答を多め＋予備を作らせ、修理はその場の予備で差し替え（新agent不要）。②各問を2案並行生成し unique な方を採用＝修理/再反証の直列段を大幅に省ける |
| 2-run監査 | 和集合（確度重視） | 2runは**元々並列**＝時間増ゼロ。速度でも維持 |
| パイロット | 原則やる（鉄則1） | 作り方に確信があれば省略可 |
| コスト感 | トークン最小 | 目安 **トークン+30〜80% / 時間−40〜70%**（波を1つに畳むため） |

**速度モードの落とし穴（2026-07-18 order一意性監査で実証）**
- **重い推論のタスクはバッチを小さく**。1体の所要 ∝ 問数 × 難度。order一意性(4!通りの並びを吟味)にバッチ40を当てたら1体が重く、**波の最後の1バッチ(straggler)が全体を律速**した。目安: 軽い判定(誤答代入)=40 / 重い判定(順列吟味・長文読解)=**15〜20**。
- **独立ラン(2-run A/B)は1つの `parallel` で全並列**にする。`await parallel(runA)` の後に `await parallel(runB)` と書くと **A→Bのバリア**になり、Aの遅い1バッチがBの全バッチを止める（＝速度モードの意味が消える）。正: `parallel([...Aの全thunk, ...Bの全thunk])` で全体を一度に流す。監査は2runとも独立なのでバリア不要。

**ガード（速度モードでも絶対）**——CLAUDE.md#8 は「乱発禁止」であって「並列禁止」ではない。速度モードは**並列上限内で意図的に**増やす、青天井にはしない:
- **1問1agentにしない**。総エージェントは「並列上限 × 数波」で頭打ち（201体・396万トークンでセッション上限到達＝実害の反面教師）。
- 起動前に「**標準 ◯分・◯Mトークン ↔ 速度 ◯分・◯Mトークン**」を提示して**ユーザーが選ぶ**（実費¥0でも判断軸は quota）。
- セッションquota残に不安があれば速度モードを選ばせない（上限到達＝全作業停止）。

### 学び（随時マージ）

- **監査は過検出前提**: 「疑わしきはflag」＋2run和集合で35%flag。三分類(multi/pair/level)×確度(both/one)で優先度化し、修理範囲はユーザーに実数提示で決める（→鉄則8）。
- **pairは同カテゴリ4択の宿命でしばしば不可避**: 正解が「同理由で誤る語のクラス」と対比される型(もしかしたら↔確信副詞・なかなか↔否定呼応)では、誤答が同理由で消せるのは正常設計。**一意なら残存pairは許容**。
- **修理役は形式を問わず第2の正解を生む**: 文法形式でも multi残存4・pair残存10 → 再反証は必須（→§3）。
- **stem起因の不良は自動置換で直らない**: 主語欠落(ましょうか↔ますか)・想起合図欠落(っけ↔ぞ)は**文の手直し＝人判断**。数件は hand-fix 提案（agentを立てない＝CLAUDE.md#2）。
- **ルビ表記ズレに注意**: 反証AIは validChoices を「食べ」等ルビ無しで返す。実選択肢「食（た）べ」と機械照合する時は**ルビを外して**照合（4件取りこぼした）。
- **Workflowの .output はラッパ**: `{summary,logs,result,...}` ＝実データは `result` 配下。解析時に注意。
- **1本のpipelineで gen→反証→修理→再反証**: flag無しの級は修理/再反証agentをスキップしてagent節約（条件分岐）。
- **order(並べ替え)の非一意=語順自由**: 副詞句・格助詞句・主題（〜で/〜に/〜は/時間句）の前後入替で★の語が変わる型が典型（公園へ↔さんぽに、本を↔百冊、今日は↔理由節）。両run一致39/片run30。除外は `ambiguous:true`（daimon.ts が BANK から filter）。既存除外296に+69=総365。
- **文章の文法(passage_grammar)の隠れギャップ**: 構造(2/1文章・5空所)は公式一致だが、空所の型が機能語60%+助詞22%＝**単文文法に偏り**、公式の核（接続詞/指示語/授受視点/伝聞推量＝結束性）が計11%と薄い。特にN3は機能語90%。作問は「流れで選ぶ」型を増やす。答え位置のindex0偏りは PassageSetPlayer がシャッフルするので無害。
- **contextFreeの過剰ゲートは自傷**: 「本文依存でなければ欠陥」で弾くと歩留まり40%→11%に崩壊。公式も本文依存は100%でなく**約79%**(N4は50%・助詞/時制/疑問詞は一文で解ける)。**正すべき欠陥は「第2の正解(非一意)」だけ**。contextFreeは許容し、生成プロンプトで結束性を主目標にする。
- **1セット=本文依存3+単文で解ける2=5空所(3:2)が公式相当で高歩留まり**: 全部結束性を強制すると難産。2個を易しい単文型(助詞/時制/疑問詞)にすると5問セットが安定(パイロット9/9・5問5・3:2達成)。
- **修理は反復(最大3周)+4/5→3+救済**: 非一意1個でセット全捨ては歩留まりを潰す。弱い空所だけ作り直しを繰り返し、無理なら本文へ答えを埋め戻してリナンバー→3〜5問で残す。
- **本文↔選択肢の重複崩れに注意**: 本文「買ってみる【5】」＋選択肢「買ってみるつもりです」＝表示で二重。生成に重複禁止を明記+組み立て時に検出。**数値(歩留まり/比率)だけ信じず実文を必ず見る**(ルビ破損・重複はスポットチェックで発見)。
- **読解の名前→役割は純機械置換だと誤爆**: 「たくさん/つまり/緑/光/先/砂糖」等を壊す。**既知名のみ作用+曖昧語はさん付き時のみ+漢字/かな別表記をエイリアス統合+漢字名をルビ（かな）ごと先に消費**(順序を誤ると「田中(Bさん)さん」化)。ドライラン→実文確認→適用が必須。
- **大問別 既存↔公式ギャップの判定(2026-07-18)**: grammar_form=**手当て**(個人名除去/会話生成/一意監査で修復)。order=**手当て**(一意監査で365除外・作り直し不要)。passage_grammar=**新規作成**(型が機能語偏重で個別手当て不可・結束性化は実質作り直し)。reading=**手当て中心**(名前置換済/一意監査・長さ較正は残)。moji_goi各種=在庫潤沢で構造一致(既存活用)。
